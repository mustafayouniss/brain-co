# Security Architecture & Cryptographic Conventions

> Source of truth for password hashing, JWT access tokens, role-based authorization, and cryptographic parameter standards.
> Verified against test suites in `backend/tests/test_security.py`, `backend/tests/test_auth.py`, `backend/tests/test_auth_rbac.py`, and `backend/tests/test_users.py`.

---

## 1. Password Hashing & Validation

### Choice & Rationale
- **Algorithm**: Argon2id (Argon2 version 19).
- **Implementation**: Direct `argon2-cffi` (pinned to `25.1.0`).
- **FastAPI Context**: While FastAPI's official tutorial demonstrates `pwdlib` with Argon2, we use `argon2-cffi` directly to eliminate intermediate wrapper layers and maintain a lean, battle-tested cryptographic surface (D-012).
- **OWASP Compliance**: Conforms with the [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), which specifies Argon2id as the primary recommended hashing algorithm due to its memory-hardness and protection against GPU/ASIC attacks and side-channel timing attacks.

### Operational Guarantees
1. **Salting**: Every password hash receives a cryptographically secure, unique salt automatically generated by `argon2-cffi`. Two identical passwords produce distinct hash strings.
2. **Length Validation**: `hash_password(plain)` requires a string of 1 to 128 characters (raising `ValueError` if empty or >128).
3. **Password Policy (D-014)**: Account provisioning (`create_user`, `POST /api/v1/users`, `create_admin` CLI) strictly enforces 12 to 128 characters. No arbitrary composition rules (no mandatory symbols/numbers).
4. **Safe Verification**: `verify_password(plain, hashed)` catches all internal verification exceptions (`VerifyMismatchError`, `InvalidHashError`, `ValueError`, `TypeError`) and returns `False` without raising.
5. **Timing Attack Mitigation for Unknown Users**: `verify_dummy_password(plain)` verifies against a precomputed dummy hash at login time when a user email is not found, ensuring uniform processing duration between existing and non-existent accounts.
6. **Rehashing Detection**: `password_needs_rehash(hashed)` exposes `PasswordHasher.check_needs_rehash`. On successful login, if parameters need upgrading, the newly hashed password is automatically saved.

## 2. JWT Access Tokens

### Algorithm & Key Management
- **Algorithm**: `HS256` (HMAC with SHA-256) strictly pinned across creation and verification.
- **Secret Key**: `SECRET_KEY` configured in `.env`, validated by Pydantic Settings to be at least 32 characters long and not match the default placeholder (`change-this*`).
- **Key Safety**: The real secret key is never committed to version control, never logged, never echoed to terminal output, and never stored in test suites (D-013).

### Token Claims
Access token payloads are strictly minimal:

```json
{
  "sub": "<user_uuid>",
  "iat": 1728400000,
  "exp": 1728403600
}
```

- `sub` (string, required): User UUID string identifier. Must be a valid non-empty UUID string.
- `iat` (UTC timestamp, required): Issued-at Unix timestamp.
- `exp` (UTC timestamp, required): Expiration Unix timestamp (default: 60 minutes via `ACCESS_TOKEN_EXPIRE_MINUTES`).
- **Excluded Fields**: Roles, email addresses, names, and passwords are never included in the JWT payload. Roles and account status are resolved on demand from the database during request authorization (T8).

### Token Validation Rules
`decode_access_token(token)` enforces:
1. `algorithms=["HS256"]` explicitly specified; algorithm `none` and symmetric/asymmetric confusion attacks are rejected.
2. `exp`, `iat`, and `sub` claims are required.
3. Expired, tampered, wrongly signed, or missing-subject tokens raise a single uniform exception: `TokenSecurityError`.

## 3. Authentication & Authorization Controls

### User Enumeration Defense (D-014)
- `POST /api/v1/auth/login`: Unknown email, incorrect password, and inactive user accounts return the **exact same HTTP 401 response** with the header `WWW-Authenticate: Bearer` and body `{"error": {"code": "UNAUTHORIZED", "message": "Invalid email or password"}}`.
- Unknown emails execute `verify_dummy_password` to ensure constant-time response behavior.

### Credential Validation Defense
- `get_current_user`: Missing `Authorization` header, malformed header, invalid token, expired token, unknown user, and inactive user all return the identical HTTP 401 response: `{"error": {"code": "UNAUTHORIZED", "message": "Could not validate credentials"}}`.
- Internal token verification error details (`TokenSecurityError`, PyJWT exception strings) are never leaked to HTTP response bodies.

### Database-Driven Role Enforcement (T8, D-014)
- `require_admin`: Depends on `get_current_user` and inspects `user.role` from the active PostgreSQL database row.
- Role is never trusted from token claims. If a user is downgraded in the database, their next request is immediately blocked with HTTP 403 `{"error": {"code": "FORBIDDEN", "message": "Insufficient privileges"}}`.

## 4. What Is NOT Built Yet (Roadmap)

The following security features are explicitly deferred beyond Ring 0:

- **Refresh Tokens**: Not implemented in Ring 0 (stateless short-lived 60-minute access tokens only).
- **Token Revocation / Blacklisting**: Not implemented. Tokens remain valid until their `exp` timestamp expires.
- **Login Rate Limiting**: Not implemented in Ring 0.
- **Breached-Password Checking**: Not implemented in Ring 0.
