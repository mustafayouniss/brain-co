# Security Architecture & Cryptographic Conventions

> Source of truth for password hashing, JWT access tokens, and cryptographic parameter standards.
> Verified against test suite in `backend/tests/test_security.py`.

---

## 1. Password Hashing: Argon2id via `argon2-cffi`

### Choice & Rationale
- **Algorithm**: Argon2id (Argon2 version 19).
- **Implementation**: Direct `argon2-cffi` (pinned to `25.1.0`).
- **FastAPI Context**: While FastAPI's official tutorial demonstrates `pwdlib` with Argon2, we use `argon2-cffi` directly to eliminate intermediate wrapper layers and maintain a lean, battle-tested cryptographic surface.
- **OWASP Compliance**: Conforms with the [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), which specifies Argon2id as the primary recommended hashing algorithm due to its memory-hardness and protection against GPU/ASIC attacks and side-channel timing attacks.

### Operational Guarantees
1. **Salting**: Every password hash receives a cryptographically secure, unique salt automatically generated by `argon2-cffi`. Two identical passwords produce distinct hash strings.
2. **Length Validation**: `hash_password(plain)` requires a non-empty string not exceeding 128 characters (raising `ValueError`).
3. **Safe Verification**: `verify_password(plain, hashed)` catches all internal verification exceptions (`VerifyMismatchError`, `InvalidHashError`, `ValueError`, `TypeError`) and returns `False` without raising.
4. **Timing Attack Mitigation for Unknown Users**: `verify_dummy_password(plain)` verifies against a precomputed dummy hash at login time when a user email is not found, ensuring uniform processing duration between existing and non-existent accounts.
5. **Rehashing Detection**: `password_needs_rehash(hashed)` exposes `PasswordHasher.check_needs_rehash` for seamless parameter upgrades upon authentication.

## 2. JWT Access Tokens

### Algorithm & Key Management
- **Algorithm**: `HS256` (HMAC with SHA-256) strictly pinned across creation and verification.
- **Secret Key**: `SECRET_KEY` configured in `.env`, validated by Pydantic Settings to be at least 32 characters long and not match the default placeholder (`change-this*`).
- **Key Safety**: The real secret key is never committed to version control, never logged, never echoed to terminal output, and never stored in test suites.

### Token Claims
Access token payloads are strictly minimal:

```json
{
  "sub": "<user_uuid>",
  "iat": 1728400000,
  "exp": 1728403600
}
```

- `sub` (string, required): User UUID string identifier. Must be a non-empty string.
- `iat` (UTC timestamp, required): Issued-at timestamp.
- `exp` (UTC timestamp, required): Expiration timestamp (default: 60 minutes via `ACCESS_TOKEN_EXPIRE_MINUTES`).
- **Excluded Fields**: Roles, email addresses, names, and passwords are never included in the JWT payload. Roles and account status are resolved on demand from the database during request authorization (Ring 0 / T8).

### Token Validation Rules
`decode_access_token(token)` enforces:
1. `algorithms=["HS256"]` explicitly specified; algorithm `none` and symmetric/asymmetric confusion attacks are rejected.
2. `exp`, `iat`, and `sub` claims are required.
3. Expired, tampered, wrongly signed, or missing-subject tokens raise a single uniform exception: `TokenSecurityError`.

## 3. What Is NOT Built Yet (Roadmap)

The following security features are deferred to later tasks or rings:

- **Refresh Tokens**: Not implemented in Ring 0 (T6-T8 focus strictly on stateless short-lived access tokens).
- **Token Revocation / Blacklisting**: Not implemented. Tokens remain valid until their `exp` timestamp expires.
- **Password Complexity Policy**: Minimum character length, character class requirements, and common-password checks are deferred to Task T9 (Admin seeding & password policy).
